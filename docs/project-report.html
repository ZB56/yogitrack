YogiTrack: Project Report, Part 2

Course: ACS 5423, Software Development for World Wide Web Institution: University of Oklahoma Application: YogiTrack, a record-keeping system for the Yoga H'om studio Increment: Application 2.0 (Part 2), the final submission Technology stack: MongoDB · Express · React · Node.js (MERN) Live application: https://yogitrack-zb-9cc3ff17df1c.herokuapp.com Repository: https://github.com/ZB56/yogitrack

This report supersedes the Part 1 report. It describes the whole application, with the Part 2 work marked throughout, so it can be read on its own.

1. Executive summary

Yoga H'om runs its studio on paper: a card per customer for classes bought and attended, and a signed sheet per class. That process does not scale and cannot answer questions like "how much do we owe each instructor this month?" without manual tallying.

YogiTrack replaces those records with a web application. All seven use cases from the course specification are implemented, and the application is deployed, with a GitHub repository and a CI pipeline that gates every release.

Part 2 also added authentication, which the Part 1 review asked for: accounts with bcrypt-hashed passwords, a signed token, and a role of manager or instructor checked on the server for every protected request. That is what finally makes the specification's two actors real; before it, "the Instructor" was a label on a diagram rather than something the application could tell apart.

What Part 2 contributes, beyond four more forms

  • A rule the system enforces about time. UC2 cannot simply save what it is given: only one class may run at a time, so a clash has to be detected and somewhere else has to be proposed. That meant settling what a class length even is, which the specification never states.
  • Money that has to add up. UC5 validates the amount against the price list, the payment date against today, and the validity window against the package's own rules, then moves a balance. It is the first place where two collections change together, so the order of those writes matters.
  • The first use case with a deliberate exception. UC6 must let an instructor check in a customer who has run out of classes, recording a negative balance to be settled later. The system's job there is to make the consequence visible, not to prevent it.
  • Questions answered inside the database. UC7's four reports are MongoDB aggregation pipelines, so joining, grouping and totalling happen next to the data rather than after it has been copied out.
  • A security boundary. Authentication is enforced in Express middleware, not in React. The interface hides what a role cannot use as a courtesy; the server is what makes it impossible.

What the whole application now does

Nine collections' worth of studio record-keeping: who teaches, who attends, what the studio sells, what is on the timetable, what has been sold, who was in the room, and what all of that adds up to at the end of the month.

2. Problem statement and background

Yoga H'om was founded in 2003 in the suburbs of Pittsburgh, offering affordable yoga education to its community. It runs classes every day, taught by a number of instructors, with a published schedule. Some classes are general; others are specialised, such as Chair Yoga for seniors or Gentle Yoga for beginners.

Customers buy class passes: a 4-class or 10-class package, a 3-month unlimited package, or a single drop-in pass. All packages have a validity period, and seniors get a discounted rate. The studio also runs workshops and special programme series at separate prices.

The current process is manual. A paper card per customer is ticked off as classes are bought and attended. A paper attendance sheet is signed at each class, recording the attendee, the package used, and the payment mode.

The problem. These manual processes have become a bottleneck to growth and operational efficiency. Records are duplicated across cards and sheets, they can only be read in one physical place, and any question spanning more than one customer requires a manual count. The studio has therefore begun automating, starting with record-keeping for instructors, customers, packages, the class schedule, and attendance.

The goal of this application is to make those records authoritative, queryable and remotely accessible, so that the studio's day-to-day work no longer depends on paper.

3. Scope

3.1 How the work was split, and why that order

The seven use cases form a dependency tree:

    Instructor ──> Class ──────────┐
    Package ───┐                   ├──> Attendance ──> Reports
    Customer ──┴──> Sale ──────────┘

A class cannot be scheduled without an instructor. A sale cannot be recorded without both a customer and a package. Attendance needs all of them, and the reports aggregate everything.

Part 1 built the three roots of the tree, which made Part 2 purely additive: not one Part 1 schema had to be redesigned to make Part 2 work. The only change to a Part 1 model in the whole of Part 2 was adding a class type to the sale snapshot, and that was a Part 2 field on a Part 2 model.

Within Part 2 the same ordering logic applied, with one exception. Authentication was built first, before any of the four use cases, even though it is not a use case at all. Two of the four needed it in order to be built correctly rather than retrofitted: UC2 sends a confirmation "to the manager", and UC6 shows "the classes assigned to the instructor". Both questions have no answer until the application knows who is signed in. Building the use cases first would have meant inventing a stand-in for the current user and then replacing it.

AddInstructor.jsx and AddCustomer.jsx are now thin wrappers that supply only what genuinely differs: the wording, which API functions to call, and where the "view all" link points. A min: 0 would make that legitimate case impossible, so the customer list highlights a negative balance instead of preventing it.

The interesting problem here is "unlimited." A 3-month unlimited package has no number of classes, and a plain number cannot represent that honestly. The chosen representation is a boolean flag with date-based validity rather than a sentinel number; the reasoning, and the rejected alternative, are in decision 4.

This shows up in the schema in a way worth pointing out. numClasses declares its required rule as a function rather than true:

numClasses: {
  type: Number,
  default: null,
  required: [function () { return !this.unlimited; },
             'Please choose how many classes this package includes.'],
  ...
}

Mongoose calls that function with the document as this, so the field is mandatory for a counted package and legitimately absent for an unlimited one. A plain required: true would have made the 3-month unlimited pass, one of the studio's seven real products, impossible to save.

Two further rules are enforced at the schema rather than trusted from the form: the class count must be one the studio actually sells (1, 4 or 10), and the end date must fall after the start date, because a package that expires before it begins can never be sold. The controller additionally forces numClasses to null whenever unlimited is true, so a contradictory request body cannot be stored in a state that later code could read two ways.

4.4 UC2: Add a class (original: Use case 2) — Part 2

Actor: Manager Data captured: instructor, day, time, class length, class type (General or Special), pay rate.

A class in YogiTrack is a weekly slot in the timetable, not a single dated occurrence. That follows the requirements: Fig. 1 is a weekly schedule and UC2 collects a day and a time rather than a date. A particular Tuesday only becomes a record when attendance is taken for it, which is also how the studio's paper sheets work.

Flow as implemented:

StepSpecificationImplementation
1Manager chooses to create a class and enters the dataAddClass.jsx
2System checks for a schedule conflict, as only one class can be held at a timeGET /api/classes/check-conflict runs as the form is filled in; POST /api/classes checks again before saving
3If there is a conflict, the system suggests other optionsUp to four free slots, offered as buttons
4Manager selects one of the optionsClicking a suggestion moves the form to that slot
5Manager confirms and publishes the scheduleSaving puts it in the schedule; there is no separate publish state
6System confirms to the manager and to the instructorsendMessage to the instructor on their preferred channel, sendStudioMessage for the manager's copy

The problem the specification leaves open: how long is a class? "Only one class can be held at any time" cannot be tested without a length, and the course documents never give one. The answer adopted is a durationMinutes field defaulting to 60 (decision 5). A field rather than a constant, because the studio runs workshops that are plainly not an hour, and because the class diagram carried durationMinutes from Part 1.

With a length, a conflict is the standard interval-overlap test, expressed as a method on the model so that the rule lives with the data it describes:

classSchema.methods.clashesWith = function (slot) {
  if (this.day !== slot.day) return false;

  const thisStart  = timeToMinutes(this.time);
  const thisEnd    = thisStart + this.durationMinutes;
  const otherStart = timeToMinutes(slot.time);
  const otherEnd   = otherStart + slot.durationMinutes;

  return thisStart < otherEnd && otherStart < thisEnd;
};

Times are stored as 24-hour "HH:MM" text and converted to minutes for the comparison. Text, because a weekly slot has no date attached and a Date would drag a timezone into a value that has none; minutes, because it turns the overlap rule into two ordinary inequalities. The comparison is strict on both sides, so touching slots do not clash and a 60-minute class at 09:00 leaves 10:00 free.

Step 3 is where this use case earns its keep. Refusing a clash is easy; proposing somewhere to put the class instead is what makes the rule usable. The alternatives are offered nearest-first in the order a manager actually thinks about them: later the same day in half-hour steps, then earlier the same day, then the same time on following days. A manager with a clash usually wants to nudge the class an hour, not move it to Sunday.

Suggestions stay inside a 06:00–21:00 studio day, which is an assumption: the requirements say the studio runs classes every day but never give opening hours. It limits only what YogiTrack proposes; a manager may still enter any valid time, which is why the schema accepts any 24-hour time.

A clash cannot be overridden, and that is the difference from UC1. The duplicate-name prompt in UC1 can be confirmed through, because two people genuinely may share a name. Two classes cannot share one room at one time, so POST /api/classes answers 409 with the alternatives and no way to force it. The HTTP status is the same; what the body offers is not.

Beyond the specification: a schedule list at /classes, for the same reason Part 1 added list views. The server narrows it to the signed-in instructor's own classes, which is exactly what UC6 step 2 needs.

4.5 UC5: Record a sale (original: Use case 5) — Part 2

Actor: Manager Data captured: customer, package, amount paid, mode of payment, date and time of payment, validity start and end.

Flow as implemented:

2System prompts for the data and auto-populates the package typeGET /api/sales/quote returns the price, the validity window and the customer's current balance; the form fills itself in
3Manager enters the dataAuto-filled fields stay editable, because the use case lists them as entered data
4System validates the dataThree rules, below
5System updates the class balance$inc on the customer document
6System displays the new balance and confirmsSuccess panel naming the package, the amount, the classes added and the new balance

The three validations in step 4, each quoted from the specification:

  • "Amount paid is as per the package rate." The amount is compared against the package's price. Prices are stored as floating-point dollars, so the comparison uses a half-cent tolerance rather than ===; the note in Package.js explains why a production billing system would store cents as integers instead.
  • "Date and time are current." Read as: the sale is being recorded as it happens, so the timestamp must be today. A future time is a typo, and an older one would be a back-dated sale, which the use case does not describe. A minute of slack is allowed because the browser's clock and the server's rarely agree to the second.
  • "Start and end dates are as per the package rules and are current." The package's own validity window gives the LENGTH ("4 Class Pass, validity one month" is stored as two dates a month apart), so buying it today gives a window of the same length starting today. The server re-derives that window and rejects anything that does not match, rather than quietly correcting it.

Errors from all three are collected and returned together, so a manager sees everything that is wrong in one pass instead of fixing three things in a row.

A sale snapshots the package it sold. packageName, classesPurchased, unlimited and classType are copied onto the sale at the moment it is recorded, as well as the packageId reference. The duplication is deliberate (decision 16): a package is editable and a sale is a historical fact. If a sale held only a reference, raising the price of the 10 Class Pass would silently rewrite every sale ever made of it, and the package sales report would show revenue the studio never took.

Step 5, and the order of two writes. The sale is written first, then the balance is incremented:

const updatedCustomer = await Customer.findOneAndUpdate(
  { customerId: customer.customerId },
  { $inc: { classBalance: classesAdded } },
  { new: true }
);

Two details. $inc rather than reading the balance and writing it back, because the increment is a single atomic operation inside MongoDB and two sales recorded at the same moment cannot lose one of them. And the sale before the balance, because if the second write failed the studio would have a recorded payment and an un-credited balance, which a manager can see and fix; the other order would credit classes with no record of payment, which nobody would ever notice.

An unlimited package adds nothing to the counter. Entitlement for it is decided by the validity dates, not by counting down (decision 4), so classesAdded is 0 and the success panel says so in words rather than reporting a balance that did not move.

Step 5 is a warning, not an error, because a class genuinely can be moved or made up on another day, and the sheet should record when it was actually held. The system's job is to make the discrepancy visible:

L00001 is scheduled for Tuesday at 09:00, but this sheet says Thursday at 09:00.

Step 8 is the most interesting rule in the specification. It requires that an instructor be able to check in a customer with no classes left, "to be resolved later". So an insufficient balance is a question, not a refusal, and it uses the same convention as UC1's duplicate name: 409 with requiresConfirmation, the names and what each balance would become, and a second request that goes ahead. Nothing in the schema prevents a negative balance either; classBalance has deliberately no minimum, and the customer list colours it instead.

What a check-in costs is decided in one place, so the preview the instructor sees while ticking names and the figure that is written on save cannot disagree:

  • <strong>1.</strong> An active unlimited package covers the class and deducts nothing.
  • <strong>2.</strong> Otherwise one class comes off the balance.
  • <strong>3.</strong> A balance that cannot cover it is flagged for step 8.

"Active" is judged at the time of the class, not the time of typing, so a sheet filed on Monday for Friday's class is judged by whether the package covered the customer on Friday.

The sheet records what the check-in did, not just who was there. Each attendee is stored as a sub-document with usedUnlimited, balanceBefore and balanceAfter. This is the one place the built model deliberately differs from the Part 1 data-model sketch, which had a plain array of customer IDs (decision 17). Step 8's negative balance is only resolvable later if the sheet says what happened, and without usedUnlimited a reader cannot tell a legitimate free check-in from a balance that failed to decrement.

One rule is reported rather than enforced, and the report says so. The requirements state that a Special package admits its holder only to Special classes. The data model the use cases specify keeps one balance per customer, not a balance per package type, so once a counted check-in is made the system cannot tell which purchase it drew on. Blocking on class type would mean enforcing a rule the data cannot support, and would wrongly refuse a customer holding both a General and a Special package. So the sheet flags "No active Special package on file" and leaves the judgement with the instructor (decision 18). The honest fix is per-package balances, which is a change to the specified data model; it is listed in section 12.

Step 10's message reproduces the specification's wording and its dd/mm/yy format exactly, including a negative balance where there is one:

Hello Priya! You are checked-in for a class on 15/10/26 at 9:00 am. Your class-balance is 15.

Actor: Manager Four reports, as the written use case names them:

Why aggregation pipelines. Each report could have been a find() followed by JavaScript. A pipeline is a list of stages that runs inside the database, so the joining, grouping and arithmetic happen next to the data instead of after every document has been copied across the network. It is also the part of MongoDB that most repays understanding, and the course asks for a design that demonstrates the stack rather than merely uses it.

Two details worth drawing out:

  • The customer report computes its labels at read time. $switch compares each sale's validity window against $$NOW, the server's clock, so a package that lapsed overnight reads as expired without anything being rewritten. Storing a status on the sale would mean every document in the collection going stale while nobody is looking.
  • The payment report filters before it joins. $match on the indexed heldAt comes first, so the $lookup runs against one month of sheets rather than the whole collection. Stage order is a performance decision, not a stylistic one.

One assumption, stated. UC7 says the payment report is "based on the pay-rate and class check-ins". The pay rate is treated as what an instructor earns each time the class is held, and a class counts as held when an attendance sheet exists for it. Paying per head would make a teacher's income depend on turnout, which is not how a studio pays. The check-in count is reported next to the payment, so both readings are visible to anyone who disagrees.

4.8 Authentication and roles — Part 2, not a use case

No course document specifies authentication, but the specification names two actors with different capabilities, and the Part 1 review asked for it directly. Decision 12 settles it as real accounts, not a role selector: a selector that anyone can switch demonstrates two views but authenticates nobody.

What was built:

PieceChoiceReason
Passwordsbcrypt, work factor 12, select: false on the hashEach increment of the factor doubles an attacker's work on stolen hashes; select: false keeps the hash out of every query result except the one the sign-in code runs
SessionsA signed JSON Web Token, eight-hour lifetimeA server-side session needs a store, and the Heroku dyno's filesystem is discarded daily. Eight hours is about one studio shift; the trade-off is that a token cannot be revoked early, which is why it is short
EnforcementrequireAuth and requireRole in Express middlewareRoles are checked on the server for every protected route. The React guard and the role-filtered navigation decide what is offered, not what is allowed
AccountsA manager creates them; no sign-up pageA studio decides who works there. The first manager comes from npm run create:manager, which reads the password from the environment and stores only the hash
Instructor linkA instructorId on the accountUC6 shows "the classes assigned to the instructor", which needs the login to know which instructor it belongs to

Two details that are easy to get wrong, and were deliberately not:

  • Every sign-in failure answers with one message. Unknown username, wrong password and deactivated account all return "Username or password is incorrect." Being more specific would turn the endpoint into a way to discover which usernames exist.
  • 401 and 403 mean different things. 401 is "I do not know who you are", and the client responds by sending the user to sign in. 403 is "I know who you are, and no", and the client shows the message. The React side clears a token on any 401 except the login call itself, because a wrong password also answers 401 and must not sign out the manager who mistyped it.

What authentication is not. The token is kept in localStorage, so a cross-site scripting bug could read it. An httpOnly cookie would be safer against that, but brings CSRF protection with it. The reasoning is written out in client/src/api/session.js, and the risk is listed in section 12 rather than left unsaid.

5.2 Class diagram

Eight collections and one embedded record. Part 2 added users, classes, sales, attendance and the embedded Attendee.

Points worth drawing out:

  • MongoDB does not enforce references. There is no foreign key and no JOIN. A sale can store a customerId matching no customer, and the database will accept it. Every reference that matters is therefore checked in the Express controller before saving; the «FK» marks denote intent, not a constraint. This is why "No customer with that id" is an error message the application produces rather than one the database raises.
  • Sale duplicates part of Package on purpose. The four snapshot fields are the subject of decision 16: a package is editable, a sale is history.
  • Attendee is drawn with a filled diamond, UML for composition: it exists only inside its sheet and has no identity of its own.
  • User points at an instructor rather than copying one. The login and the staff record cannot drift apart, and a manager account simply has no instructor to point at.
  • Derived values are marked with a leading / and are Mongoose virtuals: fullName, endTime, status, headcount. Storing them would create a second field that can disagree with the one it is built from.

  • The sheet is written before the balances change, for the reason given in section 4.5: a visible sheet with an un-deducted balance is recoverable, a silent deduction with no sheet is not.

6. Key design decisions

Eighteen decisions are recorded in full, with rejected alternatives, in 07-design-decisions.md. The ones that most shape the application are summarised here: six from Part 1, then the four that Part 2 added or settled.

6.1 Human-readable IDs come from an atomic counter

Decision. A counters collection holds one document per ID type. Each new ID is produced by findOneAndUpdate with $inc, then formatted as a prefix plus a zero-padded number: I00001, C00001.

Rejected: counting the existing documents and adding one. That is a read followed by a write, and two managers saving simultaneously would both read 12 and both write 13: a lost update, and two instructors sharing an ID. $inc is a single atomic operation inside MongoDB, so every caller is guaranteed a distinct number.

Why not just use MongoDB's _id? An ObjectId is 24 hexadecimal characters. It is correct for the database but not something a studio manager can read over the phone. Both are kept: _id for references between collections, and the readable ID for humans. The specification's requirement that instructor IDs start with I and customer IDs with C makes this unavoidable in any case.

6.2 The duplicate-name check is a two-step interaction

Decision. The form asks the server whether the name exists, via a dedicated lookup endpoint, before attempting to save. Only a match produces a prompt; confirming re-sends the save with confirmDuplicate: true.

Why not simply reject duplicates? Because the specification is explicit that two instructors may genuinely share a name. A duplicate is a question, not an error, which is why the server answers 409 Conflict with a requiresConfirmation flag rather than a 400, and why the UI renders it as a warning with two buttons rather than a red validation message.

The check is enforced on the server as well as in the browser. The client is expected to call the lookup first, but a request can always arrive without having done so, and a rule that exists only in the UI is not a rule.

6.3 Validation runs before ID generation

Decision. The controller builds the document, validates every field except the ID, then asks the counter for a number, then saves.

Why it matters. The obvious ordering, generating the ID first and letting the save fail validation, consumes a counter number on every rejected submission. A manager who mistypes twice would see the next instructor saved as I00004 instead of I00002. The gaps are harmless to the database but look like lost records to the studio.

This was found by testing rather than by design: the first implementation had the obvious ordering, and a test that deliberately submitted two invalid forms exposed it.

6.4 "Unlimited" is a flag, not a magic number

Decision. A package carries unlimited: true with numClasses: null. Entitlement for an unlimited package is decided by the validity dates on the sale, not by decrementing a counter.

Rejected: a sentinel such as numClasses: -1 or 9999. A sentinel reads as a bug to anyone reviewing the code, and every balance check and every balance display would need a special case. A boolean states what is actually meant.

This had to be settled in Part 1 even though it is exercised in Part 2, because it determines the shape of the Package schema.

6.5 Confirmation messaging is isolated behind one interface

Decision. All messaging goes through services/messaging.js, which exposes a single function: send this text to this person on their preferred channel. In Part 1 it records and returns the message, and the UI displays it. In Part 2 the body of that one function is replaced with a real provider.

Why. Three use cases (UC1, UC4, UC6) send messages. Without this boundary, swapping in a provider would mean editing three controllers. With it, the call sites never learn that anything changed. Any provider API key will live in an environment variable; no credential is ever committed.

Honesty in the UI: the stub reports delivered: false, and the interface presents the message as a preview of what would be sent. It does not claim to have sent anything.

6.6 One repository, with Express serving the React build in production

Decision. A single repository: Express at the root, React in client/. In development the two run as separate processes and Vite proxies /api to Express. In production a build step compiles the React app and Express serves the result alongside the API, as one web process.

Why. One repository means one GitHub project, one Heroku application and one pipeline, the simplest thing that satisfies the Part 2 requirements. And because the frontend only ever uses relative URLs such as /api/instructors, no application code differs between development and production. The proxy exists precisely so that the development-only difference stays in configuration rather than leaking into the code.

6.7 Authentication is real, and enforced on the server

Decision. Accounts with bcrypt-hashed passwords, a signed token carrying the role, and role checks in Express middleware on every protected route.

Rejected: a role selector in the interface. It would have demonstrated the two actors' views for a fraction of the work, and it authenticates nobody: the control that chooses the role is sitting in the browser, where anyone can change it. The Part 1 review asked for authentication, and a selector would not have been an answer to it.

Rejected: server-side sessions. They need a store, and a Heroku dyno restarts daily with its filesystem discarded, so sessions would either vanish or require another piece of infrastructure. A signed token needs no storage at all. The cost is that a token cannot be revoked before it expires, which is why its lifetime is eight hours rather than a week.

The part that matters most is where the check lives. React route guards and role-filtered navigation are courtesies: they stop a user being offered a screen that would only refuse them. The enforcement is server/middleware/auth.js, because the page's JavaScript is already in the browser and anyone can send a request with curl. Both exist; only one of them is a security boundary, and the code comments say which.

6.8 A sale snapshots the package it sold

Decision. packageName, classesPurchased, unlimited and classType are copied onto the sale when it is recorded, alongside the packageId.

Rejected: holding only the reference, which is the normal relational instinct and is wrong here. A package is editable and a sale is a historical fact. Raise the price of the 10 Class Pass and every past sale of it would silently change meaning; the package sales report would then show revenue the studio never took, and UC6 would decide a customer's entitlement from terms they never bought.

The duplication is the point, not a compromise, and the field comments in Sale.js say so, so that a later reader does not "normalise" it away.

6.9 Attendance records what a check-in did, not just who was there

Decision. Each attendee on a sheet is a sub-document holding usedUnlimited, balanceBefore and balanceAfter.

Rejected: the plain customerIds: [] array from the Part 1 data-model sketch. Two requirements rule it out. UC6 step 8 permits a check-in that leaves a negative balance "to be resolved later", and resolving it later means knowing what happened. And an unlimited customer consumes nothing at all, so without usedUnlimited nobody can tell a legitimate free check-in from a balance that failed to decrement.

This is the only place where the built model deliberately departs from the Part 1 sketch, which is why it is recorded rather than quietly changed.

6.10 Reports are aggregation pipelines, not loops

Decision. All four UC7 reports are MongoDB aggregation pipelines.

Rejected: find() followed by JavaScript. For the data a studio has, both are fast. The pipeline is still the better answer: the joining, grouping and arithmetic happen inside the database rather than after every document has been copied out of it, and the cost of the alternative grows with the collection while the pipeline's does not.

It is also the honest answer to a stack question. A MERN project that treats MongoDB as a place to put documents and does all its thinking in Node has not really used the database. $lookup, $group, $map and $switch are where MongoDB stops being a slower key-value store, and the pipelines are commented stage by stage because that is the least familiar part of the stack for someone arriving from SQL or from Java.

7.2 Express and Node

  • Express 5, which forwards errors thrown inside async handlers to the error middleware automatically. Under Express 4 an unhandled rejection in an async route leaves the request hanging forever, and the usual remedy is a try/catch in every handler. On 5 the controllers stay clean.
  • Centralised error handling. One middleware translates Mongoose ValidationError, CastError and MongoDB's duplicate-key error 11000 into the right HTTP status and a JSON body the UI can render. Unexpected errors are logged in full but returned as a generic message, so that internal paths and stack frames never reach a browser.
  • Middleware as the authorisation layer. requireAuth and requireRole are listed in front of a route, so a protected route cannot be reached without passing them, and "who may do this" is visible in the route table rather than buried in a handler. requireRole is a function that returns a middleware function, so one implementation serves every combination of roles.
  • Layered structure (routes / controllers / services / models), so that each file answers one question: which URL, what rule, what shared capability, what shape of data.
  • ES modules throughout, server and client, rather than the common mix of require on the server and import on the client.

7.3 React

  • Function components with hooks. useState for form state, useEffect for data loading, with the cleanup function guarding against a response arriving after the component has gone.
  • Controlled inputs: React state is the single source of truth for every field, not the DOM.
  • A single status value (idle | checking | saving) rather than several booleans, which cannot contradict each other the way three flags can.
  • Context for the signed-in user. The header needs their name, the navigation their role, and the route guard whether anyone is signed in at all. Threading that through every component as props would mean components that do not care about the user still having to forward it, so it is held once in an AuthProvider and read with a useAuth hook.
  • A three-state session, checking | ready, with the user alongside. Without the third state the application would show the login screen for a moment on every refresh while the stored token was being verified, and a working app would look broken.
  • React Router for client-side navigation, with a shared layout rendered once around every page, and guard routes that protect a whole group of pages rather than each page checking for itself.
  • A single API layer. No component contains a URL; they call named functions in src/api/. Note that fetch does not reject on a 4xx. A 400 is a perfectly successful round trip as far as fetch is concerned, so the status is checked explicitly and converted into a typed ApiError that carries the server's per-field messages.

9. User interface design

9.1 Principles applied

  • Mobile first. The base stylesheet describes the narrow-screen layout; media queries widen it at 640px and 900px. A studio manager with a phone at the front desk is a realistic user.
  • Design tokens. Colour, spacing, radius and shadow are CSS custom properties defined once, so the interface stays visually consistent and a change happens in one place.
  • Errors next to the field they concern, not only in a summary at the top.
  • Accessibility as a default, not an afterthought: every input is bound to its label by id; error text is linked with aria-describedby and the field is marked aria-invalid; related inputs are grouped in fieldset/legend; focus outlines are visible and never removed; touch targets are at least 44px; tables use real th/scope markup; and the prefers-reduced-motion setting is respected.
  • Honest state. Buttons are disabled and relabelled while a request is in flight ("Checking name…", "Saving…"), so the interface never looks idle while it is working.
  • The interface shows a role only what belongs to it. An instructor's navigation and home screen contain the one use case that is theirs. Screens for another role are left out entirely rather than greyed out: a greyed tile says "not built yet", which would be a lie when the answer is "not yours".
  • A warning is not an error. Part 2 introduced three situations where the system knows something is unusual but must not stop the user: a schedule clash with alternatives offered, a sheet filed on the wrong day, and a customer with no classes left. All three use the amber warning panel with the way forward in it, and the red error panel stays for things that actually failed.

9.2 Why no CSS framework

Bootstrap or Tailwind would have been quicker to start. Hand-written CSS was chosen because every rule is one that can be explained and defended, the application is small enough that a framework would add more to learn than it saves, and the result has no dependency to keep up to date. The cost is that the components had to be built by hand; the benefit is that there is nothing in the interface that is not understood.

10.5 The defects this found

A report that lists only passes is not a useful account of testing. Four real defects were found and fixed, three of them by testing rather than by reading the code.

1. A date-only string is parsed as UTC. The sale form sends "2026-10-15" from an <input type="date">, and JavaScript is specified to read a date-only string as UTC midnight. West of Greenwich that is the previous evening in local time, so a validity window starting today was rejected as starting in the past. The fix reads the parts out of a date-only string and rebuilds it as a local date; a full timestamp, which carries its own offset, is passed through untouched.

2. Adding days in milliseconds drifts across a daylight-saving change. A 30-day window added as 30 * 86400000 lands at 23:00 the evening before the intended date, because the November change makes one of those days 25 hours long. The form then showed a validity end one day short of what the server expected, and refused its own suggestion. The fix adds calendar days with setDate, which lets the Date object deal with the clock change.

Both of these are worth recording because neither is a mistake in the use case or in the logic. They are the kind of defect that only appears when a real browser, a real timezone and a real calendar meet code that looked obviously correct, and both were found by driving the actual form rather than by testing the endpoint with hand-written timestamps.

3. The sale did not record the package's class type. UC6's entitlement check compared the class's type against sale.classType, which did not exist, so every check-in was flagged "No active package of this type". The snapshot gained the field, which is where it belonged anyway by decision 16.

4. The reports screen rendered one frame of the wrong data. State set inside a React effect does not apply until the render after the one that scheduled it, so for one frame a newly chosen tab rendered against the previous report's rows. The four reports have four different shapes, so that frame read fields that were not there: React warned about missing keys, and row.classes.length would have thrown outright on a row from the sales report. The loaded report now carries the tab it belongs to, and the screen renders it only when the two agree. This one was found by reading the browser console rather than by looking at the screen, which is the argument for checking the console as a test case in its own right.

11. Deployment and the delivery pipeline

Target: Heroku, with MongoDB Atlas as the database. Chosen over zyLabs because Part 2 requires a GitHub repository, a Heroku deployment and a CI/CD pipeline regardless; building that pipeline once, for Part 1, avoids doing the work twice. The cost is an Eco dyno at roughly $5 per month.

How the production build works. heroku-postbuild runs the client build, producing client/dist. On start, server.js detects NODE_ENV=production and serves those static files alongside the /api routes, with any non-API GET falling back to index.html so that React Router handles page routes. Without that fallback, refreshing /instructors would return a 404.

Configuration and secrets. The application reads PORT, MONGODB_URI and JWT_SECRET from the environment. Locally these come from .env, which is git-ignored; .env.example documents the names with no real values. In production Heroku supplies PORT, and the Atlas connection string and the token secret are Heroku config vars. No credential is committed at any point.

JWT_SECRET is treated as mandatory in production: with NODE_ENV=production and no secret, the server refuses to start rather than falling back to something guessable, because a predictable signing key would let anyone mint their own manager token. It fails the same way a missing database URI does, as one line in the platform log that names the cause:

Failed to start server: JWT_SECRET is not set. Set it as a config var before starting in production.

process, which keeps local setup to one step and makes the weaker case obvious, since restarting signs everyone out.

Passwords are not stored at all. Only a bcrypt hash is, and the hash is excluded from every query result except the one the sign-in code runs. The first manager account is created by a one-off command that reads the password from the environment:

heroku run -a <app> MANAGER_USERNAME=studio MANAGER_PASSWORD='...' \
  npm run create:manager

11.2 Continuous integration

.github/workflows/ci.yml runs on every push and every pull request to main. Heroku is configured to deploy automatically from main and to wait for that check, so a commit that fails CI never reaches the dyno.

The job installs both halves of the project, lints and builds the React app, then boots the server against a throwaway MongoDB service container and exercises it over HTTP. What it checks, in the order it checks them:

  • <strong>1.</strong> the health endpoint answers, polled rather than slept on
  • <strong>2.</strong> an anonymous request to a protected endpoint is refused with 401
  • <strong>3.</strong> a manager account can be created and signed in to
  • <strong>4.</strong> that token opens every resource endpoint and all four reports
  • <strong>5.</strong> an invalid record is rejected with 400
  • <strong>6.</strong> a wrong password is refused with 401

The last two matter more than the four before them. A smoke test that only checks happy paths passes just as happily when validation and authorisation have been switched off.

The account and the signing secret the job uses exist only for that run, in a database that is destroyed with the container. The script runs under set -euo pipefail with a trap that stops the server, so a failing check cannot be masked by a later command succeeding, which is a failure mode the Part 1 version of this file had.

Part 2 broke this workflow, which is the point of having it. The old job curled /api/instructors anonymously; once authentication was added that answers 401, so the job would have gone red on the first push. The pipeline caught the consequence of a deliberate change at exactly the moment it was supposed to.

11.3 Two failures worth recording

Neither appeared in local testing, and both are the kind of thing that only the real platform reveals.

The first deploy failed to build: sh: 1: vite: not found. Heroku sets NODE_ENV=production for the build, and npm omits devDependencies when it is set. Vite is a devDependency, correctly so, since it is a build tool and not a runtime dependency. The result was that the client had no bundler.

The fix was npm ci --prefix client --include=dev rather than moving Vite into dependencies, which would have misfiled a build tool to work around a flag. The failure was then reproduced locally with NODE_ENV=production npm run build against a cleared node_modules, and the fix confirmed under the same conditions. The earlier local production test had missed it because NODE_ENV was not set during the install step, only the run step.

The second deploy built but crashed on boot: Failed to start server: Authentication failed. The Atlas connection string was well formed but the credentials were rejected, and resetting the database user's password fixed it.

This one is worth noting because the application behaved exactly as designed. server.js connects to the database before it starts listening, and exits with a clear message if that fails. The alternative, listening first and discovering the problem on the first request, would have produced a running app that returned confusing errors on every endpoint. The crash was the correct outcome, and the log line named the cause precisely.

A related detail: the first connection string was missing its database name (...mongodb.net/?... rather than ...mongodb.net/yogitrack?...). Mongoose would have silently connected to a database called test, and the application would have worked while writing to the wrong place.

12. Known limitations and what would come next

12.1 Honest limitations

  • <strong>1.</strong> There are no automated tests. This is the largest gap in the project. Verification is manual and documented in section 10, and the CI job in section 11.2 is a smoke test rather than a test suite: it proves the application boots and refuses the wrong people, not that UC5's validation is right. Everything in section 10 would be better as code that runs on every push, and the four defects in 10.5 are exactly the kind that a regression suite exists to stop coming back.
  • <strong>2.</strong> Messages are still not delivered. They are generated, displayed and logged, and the stub reports delivered: false. Real delivery needs a paid provider account; the interface behind which it would go has not changed since Part 1 (decision 3).
  • <strong>3.</strong> Records cannot be edited or deleted. Deliberate, and the reasoning is now stronger than it was in Part 1, because the references that a delete would have to respect actually exist (decision 9). The active flag is on every schema, so deactivation is a small change rather than a migration.
  • <strong>4.</strong> Entitlement by class type is reported, not enforced. A customer with only a General package can be checked in to a Special class, with a warning (decision 18). The specification's one-balance-per-customer model cannot support the rule it describes elsewhere; the fix is per-package balances, which changes the specified data model.
  • <strong>5.</strong> The token lives in localStorage. A cross-site scripting bug could read it. The application has no third-party scripts and renders no user-supplied HTML, which are the usual ways such a bug arrives, and the token expires in eight hours; an httpOnly cookie would be safer still, at the cost of CSRF protection and cookie configuration.
  • <strong>6.</strong> A token cannot be revoked before it expires. Deactivating an account stops the next sign-in and is re-checked on /api/auth/me, but a token already issued stays valid for its remaining lifetime. That is the trade accepted in decision 12, and the eight-hour lifetime is what bounds it.
  • <strong>7.</strong> The class schedule has no concept of a date range or a holiday. A class is a weekly slot that runs forever, because that is what UC2 specifies. Cancelling one week's class is not expressible; the instructor simply does not file a sheet for it, which the teacher payment report handles correctly but which is not the same as recording the cancellation.
  • <strong>8.</strong> Address is a single free-text field (decision 14). If a report ever needs to group customers geographically, this needs revisiting first.
  • <strong>9.</strong> No pagination anywhere. Every list endpoint returns everything, and the attendance list is capped at 100 sheets. At studio scale that is fine, and the indexes are in place; at ten years of attendance it would not be.

12.2 What a third increment would do, in order

  • <strong>1.</strong> An automated test suite, starting with the API cases in section 10: the three UC5 validations, UC6's entitlement and override, and the four reports against seeded data. These are integration tests against a real MongoDB, because the rules worth testing are mostly rules about documents.
  • <strong>2.</strong> Modify and deactivate, with the referential rules written down first: an instructor who leads classes cannot be deleted, a package with sales cannot be deleted, and the UI says why instead of failing.
  • <strong>3.</strong> Per-package balances, which would let UC6 enforce class-type entitlement rather than warn about it, and would make the customer report able to say which package a check-in actually drew on.
  • <strong>4.</strong> Real message delivery behind the existing interface, once the studio has a provider account.
  • <strong>5.</strong> Pagination and a date filter on the attendance and sales lists, which is the first thing that would hurt as the collections grow.

The conventions behind the status codes

409 is used for two different things, and the body says which.

  • A question. POST /api/instructors, POST /api/customers and POST /api/attendance answer 409 with requiresConfirmation: true when something needs a human decision: a person of that name already exists (UC1/UC4 step 3), or an attendee has no classes left (UC6 step 8). Re-send the identical body with confirmDuplicate or allowNegativeBalance to proceed. The data is not wrong; it needs confirming.
  • A refusal with a way forward. POST /api/classes answers 409 with suggestions and no override, because two classes cannot share one room at one time. The alternatives are the way forward.

401 versus 403. 401 means "I do not know who you are": the client discards the token and sends the user to sign in. 403 means "I know who you are, and no": the client shows the message. The React client treats every 401 that way except the one from the login call itself, because a wrong password also answers 401 and must not sign out the manager who mistyped.

400 carries fields, a map from field name to a sentence a studio manager can act on, which the form renders beside the offending input.
